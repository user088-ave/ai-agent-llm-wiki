💡 什麼是 AI Agent？（白話核心概念）

📜 傳統軟體 vs 單純 LLM

• 傳統軟體：依賴寫死的 if-else 規則，路徑固定且僵化。
• 單純 LLM：本質上是「無狀態的文字機率預測器」。它像離線的大腦，能聊天但無法主動改變外部真實世界。

🚀 現代 AI Agent

• 以 LLM 作為推理大腦自主管理工作流程。
• 具備三大自主能力：
  1. 代表使用者決策（分析目標並拆解）
  2. 調用外部工具（查詢資料庫、發送 API）
  3. 自行判斷結束時機（產出 Final Answer）

⚖️ 什麼時候該用 Agent？（適用邊界評估）

✅ 適合使用 Agent 的情境
  • 複雜且模糊的決策：如退款爭議審查、風險評估，無法用硬編碼規則窮舉。
  • 過於龐大脆弱的規則庫：法規審查等規則極度難以維護的系統。
  • 高度依賴非結構化資料：需要整合自然語言、PDF、多輪對話與即時回饋。
❌ 建議使用傳統腳本（Script）的情境
  • 流程完全固定且已知：若寫死 3 行程式碼即可穩定完成，絕不需要使用 Agent。
  • 要求 100% 確定性與毫秒延遲：如純粹欄位轉換或定時備份資料庫。
  • 避坑指南：切忌過度工程化，不要為了 Agent 而 Agent！

🧩 Agent 的解剖結構（四大核心積木）

🧠 推理引擎

Model & Instructions
Agent 的大腦。負責意圖理解、策略規劃與最終決策判定。

🛠️ 工具體系

Tool Registry
Agent 的四肢與感官。連結外界，負責執行查詢與真實操作。

💾 記憶系統

Memory System
短期對話工作歷史（messages）與跨任務長期持久經驗。

🔄 執行迴圈

Execution Loop
由原生 while loop 驅動狀態流轉，連結推理與工具執行。

🔄 思考與行動的節奏：ReAct 模式

ReAct = Reasoning（推理）+ Acting（行動）：讓模型交替產生「思維鏈」與「外部工具動作」的經典閉環。

1
Thought (思考)
分析使用者意圖：「我還缺少什麼資料？下一步該做什麼？」
➔
2
Action (行動)
選擇工具並輸出結構化參數（例如呼叫物流查詢函式）
➔
3
Observation (觀察)
接收工具執行的真實回傳，將結果寫回記憶進入下一輪 Thought
✨ 結束條件：當 Thought 判定已收集完畢所有線索，模型便跳出工具調用，輸出 Final Answer！

🛠️ 工具體系：分類與註冊機制（Tools & Registry）

📌 工具三大分類 (OpenAI 標準)
  • Data 查詢類：唯讀操作（查詢 DB、天氣）。風險低，自主調用。
  • Action 動作類：實質寫入（寄信、扣款、改資料）。高風險需控管。
  • Orchestration 編排類：將專職 Sub-agent 當作工具呼叫。
📋 工具註冊表（Tool Registry）職責
  • TOOL_REGISTRY 函式映射：真實 Python 函式字典（如 {"get_weather": get_weather}），負責被調用時執行。
  • TOOLS_SCHEMA 規格定義：傳給模型的工具清單，以 JSON Schema 定義函式名稱、用途與參數型別。
  • 強制結構化輸出：在 API 傳入 tools=TOOLS_SCHEMA，保證回傳合法 JSON，根絕字串解析失敗。

💾 記憶體系：短期工作記憶 vs 長期持久記憶

📝 短期工作記憶 (Working Memory)

• 形式：以 Python messages 陣列維護（system / user / assistant / tool）。
• 生命週期：僅存活於單次對話任務。
• 限制與修剪：受 Context Window 限制。過長時可透過滑動視窗、歷史摘要或工具截斷進行壓縮修剪。

🗄️ 長期持久記憶 (Long-term Memory)

• 情景記憶 (Episodic)：記錄過去任務的執行軌跡與成敗經驗，避免再次踩坑。
• 語意記憶 (Semantic)：儲存事實知識與使用者偏好，通常外掛向量資料庫（Vector DB）。
• 建議：初學者先做好短期訊息陣列管理，業務需要時再引入長期記憶。

🛡️ 安全護欄 vs 評測（Guardrails & Evals）

🛑 執行期護欄四大面向 (Guardrails)
  • 1. 輸入與範圍護欄：過濾惡意 Prompt，超出權責誠實拒絕。
  • 2. 工具執行護欄：權限讀寫隔離、金額與參數型別校驗。
  • 3. 迴圈重試煞車：限制迭代上限，防止工具死循環。
  • 4. 輸出忠實度護欄：格式檢查與防幻覺對照。
🎯 評測體系與人機協作 (Evals & HITL)
  • Guardrails vs Evals 邊界：護欄是「即時攔截硬邏輯」；評測是「離線量測任務品質與迭代指南」。
  • 人機協作 (Human-in-the-loop)：遇到大額轉帳、刪除等高風險動作，暫停並轉交人工確認。
  • 正向閉環：線上護欄攔截紀錄 ➔ 沉澱為離線測試案例。

💻 原生極簡實作：只要一個 while 迴圈

# 捨棄厚重框架，純原生 Python 揭露 Agent 狀態流轉核心 while iteration < max_iterations: iteration += 1 # 1. 調用 LLM 推理 response = client.chat.completions.create(model="gpt-4o", messages=messages, tools=TOOLS_SCHEMA) msg = response.choices[0].message messages.append(msg) # 寫入短期工作記憶 # 2. 判斷是否有工具動作需求 (Action) if not msg.tool_calls: return msg.content # 獲得 Final Answer，完成退出！ # 3. 執行本地 Python 函式並將結果塞回 Observation for tool_call in msg.tool_calls: result = TOOL_REGISTRY[tool_call.function.name](**json.loads(tool_call.function.arguments)) messages.append({"role": "tool", "tool_call_id": tool_call.id, "content": str(result)})

🚀 常見踩坑防範與編排進化路徑

⚠️ 常見三大踩坑（Failure Modes）
  • 工具死循環 (Tool Loops)：報錯時反覆重試 ➔ 解法：硬性重試煞車與引導錯誤訊息。
  • 推理漂移 (Reasoning Drift)：對話過長忘記初衷 ➔ 解法：設定步數上限與上下文修剪。
  • 提示詞注入 (Prompt Injection)：外部內容夾帶惡意指令 ➔ 解法：角色隔離與輸出校驗。
🧭 架構編排進化原則
  • 從 Single-Agent 開始：工具小於 8 個時最快、最穩、延遲最低。
  • 避免過早引入 Multi-Agent：多 Agent 容易引發無效對話（Chatter）與除錯黑洞。
  • 何時升級？：只有在單一 Agent 工具過多造成混淆，或業務部門權限隔離時，才升級 Manager 或 Handoff 模式。
